# Computer Infrastructure – FAANG Data Pipeline (Winter 25/26)

This repository contains my assessment submission for the **Computer Infrastructure** module (Winter 25/26).

The project implements a small but complete data pipeline around the FAANG stocks (META, AAPL, AMZN, NFLX, GOOG), including:

- Downloading hourly stock price data using `yfinance`
- Plotting Close prices for all five stocks
- Exposing the functionality via a command-line script (`faang.py`)
- Automating the workflow with a scheduled GitHub Actions job

The target audience is an informed computing professional who may not be familiar with the specific tools used, but is comfortable with Python, Git, and basic infrastructure and automation concepts.

---

## Repository structure

The repository is structured as follows:

- `.github/workflows/faang.yml` – GitHub Actions workflow (Problem 4)
- `faang.py` – Command-line script (Problem 3)
- `problems.ipynb` – Main notebook with all problem solutions
- `requirements.txt` – Python dependencies
- `.gitignore`
- `README.md`

The following directories are **generated at runtime** and are not tracked in the repository:

- `data/` – created by the notebook and script when downloading data
- `plots/` – created by the notebook and script when saving plots

They can always be recreated by running the notebook or the script (see below).

## Setup

### 1. Create and activate a virtual environment

From the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate      # macOS / Linux
# .venv\Scripts\activate       # Windows (PowerShell / CMD)
```

### 2. Install dependencies

With the virtual environment activated:

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```
This installs the core libraries used in the project:

- yfinance – access to Yahoo! Finance historical data
- pandas – data wrangling and CSV I/O
- matplotlib – plotting
- jupyter – running the notebook

## Command-line script (faang.py)

The file faang.py exposes the core functionality as a standalone script (Problem 3). It contains:

- `get_data()` – downloads five days of hourly FAANG data into `data/`

- `get_latest_data_file()` – selects the most recent CSV in `data/`

- `plot_data()` – loads the latest CSV and plots Close prices into `plots/`

- `main()` – orchestrates the above functions and prints the output paths

### Shebang and execution

The script starts with a shebang:

```bash
#!/usr/bin/env python3
```
On a Unix-like system (macOS, Linux), you can mark it as executable once:

```bash
chmod +x faang.py
```

### Running the script

From the repository root:

```bash
./faang.py
```

or equivalently:

```bash
python faang.py
```

This will:

- Download the latest FAANG data into `data/` using `get_data()`.
- Generate a plot of the Close prices into `plots/` using `plot_data()`.

This allows the pipeline to be run without opening the notebook, which is closer to how scripts are used in production environments.

## Automation with GitHub Actions

The GitHub Actions workflow in `.github/workflows/faang.yml` is the solution for **Problem 4**.

Key characteristics:

- Workflow name: **“Run FAANG script”**

- Triggers:
    
    - Automatically every Saturday at 08:00 UTC using a cron schedule: 0 8 * * 6
    - Manually via `workflow_dispatch` from the GitHub **Actions** tab

- Runs on: ubuntu-latest

- Steps:

	**1.**	Check out repository – uses `actions/checkout@v4` to clone the repo onto the runner.
	
    **2.**	Set up Python – uses `actions/setup-python@v5` to install and configure Python 3.9.
	
    **3.**	Install dependencies – installs from `requirements.txt` if present; otherwise, directly installs `yfinance`, `pandas`, and `matplotlib`.
	
    **4.**	Run FAANG script – runs `python faang.py`.

This demonstrates a simple CI-style scheduled job that runs the data pipeline automatically once a week.

## Research and references

The implementation is based on well-known libraries and documented patterns. In particular:

- **`yfinance`**  
  I used the official `yfinance` documentation and examples to understand how to call `yf.download()` with parameters such as `period="5d"` and `interval="1h"`, and how multiple tickers are returned in a single MultiIndex DataFrame.   
  - Project page: <https://github.com/ranaroussi/yfinance>  
  - Docs: <https://ranaroussi.github.io/yfinance/>  
  These guided the decision to request 5 days of hourly data for the FAANG tickers in a single call and then work with the resulting hierarchical columns.

- **`pandas` (MultiIndex and time series)**  
  The way the FAANG data is structured—with fields like `Open`, `High`, `Low`, `Close` and one column per ticker—is a natural fit for `pandas.MultiIndex`. I referred to the official pandas user guide on MultiIndex and advanced indexing, as well as tutorial-style articles on working with MultiIndex DataFrames.   
  - MultiIndex reference: <https://pandas.pydata.org/pandas-docs/stable/reference/api/pandas.MultiIndex.html>  
  - MultiIndex user guide: <https://pandas.pydata.org/pandas-docs/stable/user_guide/advanced.html#multiindex-advanced-indexing>  
  These resources influenced the choice to:
  - Keep the MultiIndex columns when reading the CSV,
  - Select the `"Close"` level to build a `close_df` DataFrame,
  - Use a `DatetimeIndex` on the rows to simplify plotting and resampling.

- **`matplotlib` (time series plotting)**  
  For plotting multiple time series on the same axes, I followed common patterns from Matplotlib tutorials and time series guides: using `fig, ax = plt.subplots()`, plotting each series in a loop, formatting the x-axis for dates, and saving the figure to PNG.   
  - Example time-series tutorials:  
    - <https://www.statology.org/how-to-plot-time-series-data-in-python-using-matplotlib/>  
    - <https://python-graph-gallery.com/basic-time-series-with-matplotlib/>  
  These influenced details such as:
  - Converting the index to `datetime` before plotting,
  - Calling `fig.autofmt_xdate()` to make date labels readable,
  - Including axis labels, a legend, and a title with the most recent date.

- **GitHub Actions (CI workflow structure)**  
  The GitHub Actions workflow follows the standard structure recommended in the official documentation and in guides that explain `actions/checkout` and `actions/setup-python`.   
  - GitHub Actions docs: <https://docs.github.com/en/actions>  
  - `actions/checkout`: <https://github.com/actions/checkout>  
  - `actions/setup-python`: <https://github.com/actions/setup-python>  
  These references shaped the pattern:

  1. **Checkout the repository** so the runner can see `faang.py`.
  2. **Set up Python 3.9** to match the local development environment.
  3. **Install dependencies** from `requirements.txt` (or fall back to explicit `pip install`).
  4. **Run the script** with `python faang.py`.

  The use of `schedule` with a cron expression like `0 8 * * 6` comes directly from the GitHub Actions scheduling documentation and satisfies the requirement to run the job every **Saturday morning (08:00 UTC)**.

### How these references influenced the design

These references are not just listed; they directly influenced specific design decisions in the project:

- **Multi-ticker data handling:**  
  Examples from `yfinance` and pandas MultiIndex guides showed that a MultiIndex `(field, ticker)` layout is the default for multi-ticker downloads. This led to using MultiIndex-aware operations such as `df["Close"]` to obtain a DataFrame of Close prices for all FAANG tickers in one step.

- **Reproducibility and file naming:**  
  Tutorials and best practices for data pipelines emphasize reproducibility and avoiding accidental overwrites. This motivated the use of **timestamped filenames** (e.g. `YYYYMMDD-HHmmss.csv` and `.png`) so each run of the pipeline creates a new artefact rather than overwriting old ones.

- **Separation of concerns in CI:**  
  GitHub Actions examples follow a consistent pattern of `checkout → setup Python → install dependencies → run script`. I mirrored that pattern in `faang.yml` to keep the workflow understandable to anyone familiar with standard CI conventions.

- **Scheduling strategy:**  
  The workflow uses a **weekly cron schedule** (`0 8 * * 6`) that directly encodes “run every Saturday at 08:00 UTC”. This choice satisfies the module requirement (“run every Saturday morning”) while aligning with the documented syntax for scheduled workflows.

Overall, the project is intentionally aligned with established practices so that another developer (or marker) can easily recognize the patterns, verify the behaviour against the documentation, and extend the pipeline if needed.
